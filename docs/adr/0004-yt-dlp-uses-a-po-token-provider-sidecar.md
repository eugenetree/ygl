# yt-dlp gets YouTube PO tokens from a sidecar

The scraper's yt-dlp calls carry a proof-of-origin (PO) token generated by a
`pot-provider` sidecar (`brainicism/bgutil-ytdlp-pot-provider`) that shares the
scraper container's network namespace, with the matching
`bgutil-ytdlp-pot-provider` pip plugin in the scraper image. `YtDlpClient`
points every invocation at it. yt-dlp's JS runtime is node, which the
ytdlp-nodejs wrapper already selects (`--js-runtime node`), so no runtime is
installed or configured.

## Why

YouTube runs two checks on player requests: IP reputation and client integrity.
The scraper egresses through a datacenter VPN, which fails the first check
(`Sign in to confirm you're not a bot`, or a bare `Video unavailable`). Account
cookies pass that check but switch yt-dlp to clients that need a PO token to
receive stream URLs, which fails the second (`The page needs to be reloaded`,
`This video is unavailable`). The token satisfies the second check for every
client and is what the bgutil project exists to provide for the first.

## Considered alternatives

- **`--ignore-no-formats-error`** — the scraper only reads metadata and caption
  tracks, which YouTube still returns when it withholds stream URLs, so telling
  yt-dlp that "no formats" is not fatal would have unblocked it with no
  infrastructure. Rejected: the same rule turns every playability error
  (members-only, age-restricted, geo, removed, premiere, bot challenge) into a
  warning plus metadata, so skip classification would have to be re-derived from
  stderr and a blocked response could be persisted as "video has no captions".
  It also does nothing for a future audio download, which needs stream URLs.
- **Cookies only** — works while the account's session is valid and YouTube
  keeps serving cookie-bearing clients without a token; it did neither by
  September 2026. Kept as an optional fallback (`YTDLP_COOKIES_B64`), on a
  dedicated account, for when tokens alone are still challenged.
- **A residential/cleaner egress IP** — removes the first check entirely.
  Orthogonal to this decision; still worth doing if challenges persist.
- **Script mode of the provider** (spawn a Node process per token) instead of
  the HTTP server — rejected: slower and, per its README, poor under
  concurrency. The server keeps the BotGuard VM warm; a token costs
  milliseconds on the local socket and no measurable change per video.

## Consequences

- The sidecar uses `network_mode: "service:scraper"` so tokens are minted
  through the same VPN exit yt-dlp uses and the provider is reachable at
  `127.0.0.1:4416` without publishing a port. It is only as up as the scraper
  container.
- Google changes BotGuard periodically; when tokens stop being accepted, bump
  the provider image tag and the pip package together (yt-dlp itself needs the
  same care already).
- `YTDLP_POT_PROVIDER_URL=` (empty) runs yt-dlp without a provider — the escape
  hatch if the sidecar misbehaves.
- A PO token does not guarantee acceptance; IP reputation still matters. The
  bot challenge is now reported as `YouTube bot challenge: …` so the alert says
  which check failed.
- A token does not lift YouTube's request rate limit either (the yt-dlp wiki
  cites ~300 videos/h as a guest, ~2000/h with an account; exceeding it shows
  up as empty `200` caption responses — `Did not get any data blocks`). Every
  yt-dlp run therefore carries `--sleep-requests`/`--sleep-subtitles` and the
  video worker pauses 5–10 s between videos.
- `curl_cffi` is installed alongside the plugin so yt-dlp can impersonate a
  browser TLS fingerprint where the extractor asks for it (captions, player);
  without it yt-dlp warns and sends those requests bare.

## When to reopen

If yt-dlp starts bundling a token provider, or YouTube stops requiring tokens
for the clients the scraper uses, the sidecar can go. If audio downloads are
added, this decision is a prerequisite, not a blocker: stream URLs need the
same token.
