# PRD: Captions persistability gate + `CAPTIONS_MISSING_DURATIONS` status

## Problem Statement

When YouTube returns a manual caption track whose events all lack `dDurationMs` (a real defect observed on video `QackTJWqOjA`), the current parsing pipeline silently drops every event because of a strict Zod schema, producing an empty `Caption[]`. Downstream, `ProcessVideoEntryUseCase` enforces an invariant *"manual and auto caption arrays must both be non-empty or both empty"* and fails the entire video processing with `UNEXPECTED_STATE`. The video is never persisted; we lose the row entirely and the failure recurs on every retry.

A second, broader issue: the array-length invariant conflates two distinct concerns — *"are captions of acceptable quality?"* (analysis concern) and *"should rows be stored?"* (persistence concern). Today these decisions live in different places with no shared vocabulary.

## Solution

Move the "should we store these caption rows?" decision into a single explicit **persistability gate** in the use case, expressed in terms of the existing `*CaptionsStatus` enums. Add a new manual-only status `CAPTIONS_MISSING_DURATIONS` to classify the degenerate-track case, and relax the extractor schema so degenerate events parse instead of being silently dropped.

The gate's rule: caption rows are inserted iff **both** `autoCaptionsStatus` and `manualCaptionsStatus` are in the `PERSISTABLE_CAPTION_STATUSES` set. Persistable statuses are those whose underlying data is *structurally sound enough that re-running validators with future rule changes could yield a different verdict without re-fetching from YouTube*. Non-persistable statuses describe either "no data" or "structural defect that no future rule change can fix".

## User Stories

1. As a developer running the scraper, I want videos with degenerate manual caption tracks to persist their metadata, so that the pipeline does not fail and I do not waste retries on a known-unsalvageable input.
2. As a developer, I want a single explicit gate that decides whether caption rows are stored, so that the persistence rule is not hidden inside an invariant designed for something else.
3. As a developer doing analytics, I want a precise status (`CAPTIONS_MISSING_DURATIONS`) on the video row, so that I can count and inspect this YouTube defect class directly via SQL.
4. As a developer revisiting validator thresholds (e.g. lowering `MIN_TOTAL_WORDS`), I want previously-stored "too short" captions to still exist in the DB, so that I can re-validate them without re-scraping YouTube.
5. As a developer revisiting overlap detection, I want previously-stored "overlapping" captions to still exist in the DB, so that I can re-classify them under looser rules.
6. As a developer, I want the "captions stored as a pair" invariant preserved, so that similarity scoring and downstream consumers can keep assuming paired existence.
7. As a developer, I want videos with `CAPTIONS_MISSING_DURATIONS` to not enqueue a transcription job (because auto captions, when present, are still valid), so that I do not waste GPU time on cases where YouTube already provided usable auto captions.
8. As a developer, I want extractor events with missing `dDurationMs` to parse with `duration: 0` instead of being silently dropped, so that the classifier can see them and act on them.
9. As a developer adding future status values (e.g. for new YouTube defect classes), I want a single `PERSISTABLE_CAPTION_STATUSES` constant to update, so that storage policy is centralized.
10. As an operator reading scraper logs, I want the failed-video processing rate to drop because `UNEXPECTED_STATE` no longer fires on this class of input, so that real errors are easier to spot.
11. As a developer using `hasValidCaptions` in callers (e.g. `video-entries.worker`), I want its semantics unchanged (true iff both sides `CAPTIONS_VALID`), so that no caller behavior changes.
12. As a developer reading the DB, I want the invariant *"`autoCaptionsStatus = manualCaptionsStatus = CAPTIONS_VALID` ⇒ rows in `captions` table"* to remain true, so that consumers (Elastic sync, channel-priority, stats) can trust their `WHERE` filters.

## Implementation Decisions

**Persistability set.** `PERSISTABLE_CAPTION_STATUSES = { CAPTIONS_VALID, CAPTIONS_TOO_SHORT, CAPTIONS_MOSTLY_UPPERCASE, CAPTIONS_HAS_OVERLAPPING_TIMESTAMPS }`. All other statuses (`CAPTIONS_ABSENT`, `CAPTIONS_NOT_FETCHED`, `CAPTIONS_EMPTY`, `CAPTIONS_MISSING_DURATIONS`) are non-persistable. Rationale: persistable = data is structurally sound and re-validation is meaningful.

**New status.** Add `CAPTIONS_MISSING_DURATIONS` to `ManualCaptionsStatus` only (not auto). The defect has only been observed on manual tracks; auto tracks are freshly generated by YouTube's ASR per request and have not exhibited this failure mode. Column is `varchar` — no SQL migration.

**Detection layer.** `ManualCaptionsValidator` gains a new check, run *before* the overlapping-timestamp check (which assumes valid timings): if `captions.length > 0 && captions.every(c => c.duration === 0)` → return failure `CAPTIONS_MISSING_DURATIONS`. Detection lives in the validator (not at the yt-api boundary) so all caption-quality judgments live in one layer.

**Extractor schema.** `eventSchema.dDurationMs` becomes optional, defaulting to `0`. Without this change, the degenerate events fail `safeParse` and are silently dropped, leaving `[]` for the validator to see — losing the signal. Note this is the *only* way to detect `CAPTIONS_MISSING_DURATIONS`: keeping the schema strict makes a degenerate track and a genuinely empty track produce byte-identical `[]` input to the validator, so the two cases become indistinguishable downstream.

- **Relaxation stays surgical.** Only `dDurationMs` is loosened. `tStartMs`, `segs`, and `utf8` remain required — they are identity-bearing, so an event missing them is genuinely unusable and *should* still be dropped. Do not loosen them to "fix" unrelated parse failures.
- **Document the *why* at the schema.** Add a comment on the `dDurationMs` field (mirroring the existing `tOffsetMs` comment) explaining that it is optional because YouTube omits duration on degenerate manual tracks, classified downstream as `CAPTIONS_MISSING_DURATIONS`. Without this, a future reader may re-tighten the schema and silently reintroduce the original bug.
- **`default(0)` over a nullable type.** Keep `duration: number` rather than introducing `number | null`. The `0` sentinel cannot cause a false positive because the detection predicate requires *every* event to be `0` (a defect-only condition), and a nullable type would ripple into the DB column, similarity scoring, and every consumer for no real benefit.
- **Shared schema, manual-only status.** `eventSchema` is shared by manual and auto extraction, so this relaxation also affects the auto path (where `dDurationMs` is the fallback for the last segment's `endTime`). This is acceptable — auto has not exhibited the defect and does not receive the new status — but the change is not manual-only even though the status is.

**Persistability gate.** `ProcessVideoEntryUseCase`:
- Remove the array-length `UNEXPECTED_STATE` failure.
- After `CaptionAnalysisService.analyze` yields per-track statuses, compute `shouldPersistCaptions = isPersistable(autoStatus) && isPersistable(manualStatus)`. Strict pair — both sides must be persistable.
- If `false`, call `videoRepository.createWithCaptions` with empty caption arrays. Video metadata still persists; per-track statuses are recorded truthfully.
- `hasValidCaptions` return logic unchanged (still requires both `=== CAPTIONS_VALID`).
- Transcription-enqueue branch (`manual = PRESENT_NOT_FETCHED && auto = ABSENT`) unchanged.

**yt-api layer.** No changes. `CaptionTrackState` remains 3-state (`ABSENT | PRESENT_NOT_FETCHED | FETCHED`). The boundary stays simple; quality and persistability are downstream concerns.

**Module shape.** No new modules. The change consists of: status enum widening (2 files), schema relaxation (1 file), one new validator branch (1 file), persistability gate + helper (1 file for helper + use-case edit). Small surface area; reversal cost is low.

## Testing Decisions

Tests cover external behavior at the seam of each affected module:

- **`ManualCaptionsValidator`**: input of 10+ captions all with `duration: 0` returns failure `CAPTIONS_MISSING_DURATIONS`. Existing tests for overlap / short / uppercase remain green.
- **`captionsExtractor`**: an event without `dDurationMs` produces a manual caption with `duration: 0` (previously was dropped).
- **`ProcessVideoEntryUseCase`** (rewrite/extend existing test file):
  - Remove the obsolete `"returns UNEXPECTED_STATE when manual captions exist without auto captions"` test.
  - Manual analyzed as `CAPTIONS_MISSING_DURATIONS` + auto `CAPTIONS_VALID` → `createWithCaptions` called with both arrays empty, video metadata persisted, both statuses recorded, no transcription enqueued, `hasValidCaptions: false`.
  - Both sides analyzed as `CAPTIONS_TOO_SHORT` → `createWithCaptions` called with **non-empty** caption arrays (both persistable), `hasValidCaptions: false`.
  - Existing happy-path test (`CAPTIONS_VALID` + `CAPTIONS_VALID`) still passes unchanged.

Prior art for these patterns lives in:

- `manual-captions.validator.test.ts` — per-rule unit tests using fixture captions.
- `process-video-entry.use-case.test.ts` — mocked dependencies, asserts on `createWithCaptions` calls and return shape.

A good test asserts only on what callers observe: which repository methods are called with which arguments, and what the use case returns. It does not reach into internal helpers or assert call ordering beyond what affects correctness.

## Out of Scope

- SQL migration. Status column is `varchar`; the new enum value is accepted by the existing schema.
- Retroactive reprocessing of videos that previously failed with `UNEXPECTED_STATE`. A separate one-off script can re-trigger them; not part of this PRD.
- Adding `CAPTIONS_MISSING_DURATIONS` to `AutoCaptionsStatus`. Auto tracks have not exhibited this failure mode; add later if observed.
- Splitting the persistability set into nuanced subsets (e.g. "persistable but flagged for review"). Single boolean is sufficient today.
- Changes to yt-api `CaptionTrackState`. An earlier-discussed `FETCHED_UNUSABLE` variant was considered and rejected in favor of keeping defect classification in the validator layer.
- Changes to similarity-scoring logic, transcription-job enqueuing, or the Elastic sync filter. Their existing `CAPTIONS_VALID`-based filters automatically continue to exclude the new status correctly.

## Further Notes

- The persistability set codifies a previously implicit storage policy. Future status additions force an explicit decision: "is this re-validatable later?" → put it in the set; "is this a structural dead-end?" → leave it out.
- A consequence of the gate: video rows with persistable-but-not-`VALID` statuses on both sides will now have caption rows in the DB even though they don't pass quality. This is new behavior. Current consumers (`elastic-captions-sync.repository.ts`, `channel-priority.service.ts`, `stats.repository.ts`) all filter on `*CaptionsStatus === 'CAPTIONS_VALID'` and so are unaffected. Future writers must remember this filter is load-bearing.
- ADR not warranted: change is reversible, the trade-offs were minor, and the design is unsurprising for anyone reading the validator + use-case together.
